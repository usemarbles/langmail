# Spec 02 — Token-savings benchmarks & pitch reframe

**Status:** draft
**Priority:** P0

## Problem

The current top-of-README pitch is *"Fast, typed, Rust-powered."* Parsing speed is not a bottleneck for any real consumer — the LLM call dominates per-email latency by 2–3 orders of magnitude. So "Rust-fast" doesn't convert the audience langmail is actually built for (AI app developers).

The real value is **fewer tokens → cheaper LLM calls → better classification signal-to-noise ratio**. That's not currently claimed anywhere with a number attached.

## Goal

Replace the speed pitch with a quantified quality/cost pitch, backed by a reproducible benchmark harness.

## Headline claim (template)

> On a 10,000-email corpus, langmail reduces prompt size by **X%** and improves Haiku classification F1 from **Y → Z** on a 5-class intent task, at a cost of **<N ms per email**.

Real numbers to be generated by the harness; the structure is the claim.

## Benchmark harness

Lives in `bench/` at repo root.

**Corpus**: Public + synthetic emails with redacted PII.
- Enron (Avocado subset or Kaggle cleaned dump) for real business mail.
- A synthetic marketing-email generator (we own this — shape, not content, matters).
- A synthetic reply-chain generator (3–7 message threads).
- Target total: ≥5,000 messages across 4 categories (business, marketing, transactional, personal).

**Metrics per email**:
- Raw body length (chars / tokens).
- langmail-cleaned body length (chars / tokens).
- Token count via `tiktoken` (OpenAI) and `@anthropic-ai/tokenizer` (Claude).
- Preprocessing wall-clock.

**Classification benchmark**:
- Fixed prompt, fixed model (Haiku 4.5), fixed 5-class taxonomy.
- Run the same prompt on (a) raw body, (b) `html-to-text` output, (c) langmail output.
- Ground truth is either human-labelled or synthetically generated with known labels.
- Report precision/recall/F1 per class and macro-averaged.

**Output**: `bench/results/<date>.json` + a README table committed to the repo.

## Surface for users

New page `docs/benchmarks.md` with:
- Headline numbers prominently.
- Methodology section.
- Link to `bench/` so anyone can reproduce.
- "Run it on your data" — one-command CLI: `npx langmail-bench --glob './emails/*.eml'` that outputs the same metrics on the caller's own corpus. No LLM call required in the default mode (token delta only); `--classify` enables it and asks for an API key.

## README restructure

- Move "Features" and "Performance" below "Why langmail" (new section).
- "Why langmail" opens with the headline number.
- Old "Performance" section stays but is retitled "Preprocessing cost" and explicitly frames Rust speed as "preprocessing overhead is negligible vs. the LLM call" — not as the lead selling point.

## Scope

**In:**
- Benchmark harness under `bench/`.
- `langmail-bench` CLI as a thin package under `packages/langmail-bench/`.
- Published numbers on `docs/benchmarks.md` and in the README.

**Out:**
- Continuous benchmarking CI (can be a follow-up).
- Comparison with every parser on the market — focus on raw, `html-to-text`, `mailparser + html-to-text` as the three meaningful baselines.

## Success criteria

- Top of the README leads with a concrete number, not an adjective.
- Any skeptic can clone, run `pnpm bench`, and reproduce the headline within 10 minutes.
- `langmail-bench` lets a user quantify the win on their own mailbox before adopting.

## Risks

- Public email corpora are noisy / not representative. Mitigation: synthetic corpora for marketing + reply chains where public data is weakest.
- Classification improvements may be small on very short emails. Mitigation: report by email-length bucket so large improvements on long/HTML emails don't get diluted.
